Connect AI assistants to **CATIA and LucidShape** through the [Model Context Protocol](https://modelcontextprotocol.io/) for geometry import, model inspection, ray tracing, photometric analysis, and IES export.

[Quick start](#quick-start) · [Client configuration](#client-configuration) · [Tool reference](docs/tools.md) · [Scene configuration](docs/generalization.md) · [FAQ](docs/installation.md#常见问题) · [Development guide](docs/development.md)

## Features

- **CAD and optical software integration**: Inspect CATIA parts, export STEP/STL, connect to an existing LucidStudio session, and import geometry.
- **Simulation and photometric analysis**: Inspect saved models, run CPU ray tracing and parameter sweeps, compare LID/IES data, and export IES files.
- **Configurable optical scenes**: Define geometry regions, materials, light source coordinates, operating cases, and detectors in JSON, with boundary diagnostics and clearly labeled GPU comparison runs.
- **Traceable jobs**: Preserve input snapshots, hashes, native logs, and result validation, with tools to query job status, list jobs, and cancel them.

Application operations use CATIA COM, LucidStudio DDE, and fixed LucidShell templates. The server communicates with clients over local stdio and controls the software through its native interfaces.

## Requirements

- **Windows** and **Python 3.11+**; Python 3.12 64-bit is recommended.
- An installed and appropriately licensed copy of **LucidShape**, with the actual path to `lush.exe`.
- For CATIA tools, **CATIA** must be installed and running; the bootstrap script installs the Windows COM dependencies.
- An MCP client that can launch a local stdio server.

The native interfaces are based on the validated LucidShape 2.0 implementation. Some extensions are tied to an engine hash; other versions require revalidation. Users must provide the software, licenses, and project inputs.

## Quick start

### 1. Install

Download or clone the source, open PowerShell in the project root, and run:

```powershell
py -3.12 scripts/bootstrap.py --lucidshape-exe "C:\Program Files\LucidShape\BIN64GPU\lush.exe"
```

Replace the path with your local `lush.exe` path. The script creates an isolated environment, installs dependencies, generates client configuration files in `local-data/config/`, and verifies MCP startup. The first installation requires network access or a usable pip dependency cache.

Add `--with-geometry` for OCCT geometry inspection. To check only the MCP server, run `py -3.12 scripts/bootstrap.py --minimal`. See the [installation guide](docs/installation.md) for more options.

### 2. Connect a client

Choose the appropriate file from `local-data/config/`, merge its server entry into your client's existing configuration, and reconnect MCP. The bootstrap script does not modify global client settings.

| Client | Generated file |
| --- | --- |
| Claude Desktop / Claude Code | `claude-desktop.local.json` / `claude-code.local.json` |
| Cursor | `cursor.local.json` |
| VS Code / Copilot CLI | `vscode.local.json` / `copilot-cli.local.json` |
| Codex | `codex.local.toml` |
| OpenCode | `opencode.local.json` |
| Other clients | See [all 14 configurations](docs/harness-compatibility.md#客户端与配置文件) |
| DeepSeek Harness (DSH) | No generated file — install a configuration-only bundle; see [DSH setup](docs/dsh.md) |

Configurations use your local interpreter and absolute paths. Regenerate them after switching computers or moving the project directory.

### 3. Make your first request

Once connected, ask the assistant to check the server's capabilities:

```text
Call get_capabilities in LucidShape MCP and list the currently enabled tools and configured engine path.
```

When your model is ready, try:

```text
Inspect D:\OpticalProjects\demo\scene.lue and list its light sources, materials, sensors, and geometry objects.
```

You can also check the installation from a terminal:

```powershell
local-data\venv\Scripts\python.exe -m lucidshape_mcp check
```

`check` verifies the protocol connection and tool discovery. Validate the native engine, licensing, and GPU capabilities separately using the MCP `health_check` tool and a small scene.

## Client configuration

Use the configuration generated by the bootstrap script where possible. The server entry point is `python -m lucidshape_mcp` or `lucidshape-mcp`; running it without arguments starts the stdio server.

<details>
<summary>Manual configuration: generic mcpServers JSON</summary>

Replace the example paths below with your actual paths. Clients such as VS Code and OpenCode use different structures; use the corresponding generator output for those clients.

```json
{
  "mcpServers": {
    "lucidshape": {
      "command": "C:/tools/lucidshape-mcp/local-data/venv/Scripts/python.exe",
      "args": ["-m", "lucidshape_mcp"],
      "env": {
        "LUCIDSHAPE_EXE": "C:/Program Files/LucidShape/BIN64GPU/lush.exe",
        "LUCIDSHAPE_WORK_DIR": "C:/lucidshape-jobs",
        "LUCIDSHAPE_TOOLSETS": "core,studio,catia,geometry,analysis,simulation",
        "LUCIDSHAPE_TOOLS": "",
        "LUCIDSHAPE_READ_ONLY": "false",
        "LUCIDSHAPE_ALLOWED_ROOTS": "[]",
        "LUCIDSHAPE_ALLOW_SOURCE_WRITES": "false"
      }
    }
  }
}
```

A ready-to-copy file is available at [mcp.example.json](examples/mcp.example.json). Keep personal configuration in `local-data/` and out of Git.

</details>

<details>
<summary>Environment variables and tool permissions</summary>

| Environment variable | Purpose / default |
| --- | --- |
| `LUCIDSHAPE_EXE` | Absolute path to `lush.exe`; native batch jobs cannot be submitted if unset |
| `LUCIDSHAPE_WORK_DIR` | Job directory; defaults to `.lucidshape-mcp/work` under the user's home directory |
| `LUCIDSHAPE_KERNEL_PATH` | Optional path to an external OCP runtime; alternatively, install the `geometry` dependencies |
| `LUCIDSHAPE_TOOLSETS` | Defaults to `core,studio,catia,geometry,analysis,simulation`; `all` includes the experimental group and legacy aliases |
| `LUCIDSHAPE_TOOLS` | Comma-separated selection of tool names; core tools are always retained |
| `LUCIDSHAPE_READ_ONLY` | Exposes only queries that protect source files and CAD state; defaults to `false` |
| `LUCIDSHAPE_ALLOWED_ROOTS` | JSON array of allowed input directories; defaults to `[]`, using the local user's access permissions |
| `LUCIDSHAPE_ALLOW_SOURCE_WRITES` | Allows `catia_show_all` to save source documents; defaults to `false` |

Installation, `configure`, and `serve` also support `--toolsets`, `--tools`, `--read-only`, `--allow-root`, and `--allow-source-writes`. See [jobs and permissions](docs/operations.md) for their scope.

</details>

## Tools and workflows

Version **0.8.0** exposes **40 tools** by default, or **49** with `experimental` enabled. The `all` selection adds 8 legacy aliases, for a total of **57**. The client's `tools/list` response is the authoritative source for tool parameters and return schemas.

| Task | Common tools |
| --- | --- |
| Inspect and export CAD | `catia_inspect_part`, `catia_export_step`, `inspect_cad_geometry` |
| Connect to an existing LucidStudio session | `studio_get_live_state`, `studio_inspect_current`, `studio_import_step` |
| Process saved models | `inspect_model`, `simulate_model`, `run_parameter_sweep` |
| Analyze and export light distributions | `analyze_lid`, `compare_photometry`, `export_ies`, `studio_export_photometry_view` |
| Generate native road and driver views | `generate_road_views`, `studio_generate_static_road_views` |
| Manage jobs | `get_job`, `list_jobs`, `cancel_job`, `read_job_log` |

For example, generate a light distribution file from a model with its light sources, materials, and sensors already configured:

```text
Run a simulation with 10000 rays using D:\OpticalProjects\demo\scene.lue.
After the job succeeds, analyze the photometric results, export IES, and provide the output file paths.
```

Batch tools return a `job_id`. At each step, poll `get_job` and confirm `status == succeeded` before using the results. See the [tool reference](docs/tools.md) for full details.

For custom scenes, use the [optical-scene/1 configuration](docs/generalization.md), which supports 1–64 light sources sharing a RAY file, custom coordinate bases, named operating cases, and per-material losses. Start with the [scene example](examples/optical-scene.example.json) and [geometry manifest](examples/region-manifest.example.json), and populate them using your actual inputs and inspection reports.

## Support scope

- **Clients**: The formats and MCP SDK startup paths for 14 configurations have been validated. Each client application and version still needs testing. The current transport is local Windows stdio; remote HTTP, WSL/containers, and cloud execution require additional adaptation.
- **Optical computation**: General scene combinations still require native optical and convergence validation. `trace_optical_gpu_control` explicitly omits additional absorption per complete traversal; the GPU candidate with fixed loss per complete traversal remains disabled. Replaying exit RAY data recalculates sensors only.
- **Engineering conclusions**: IES export does not include GB/ECE compliance certification or C-NCAP scoring. Native models may contain scripts, so use trusted inputs; path policies are not a sandbox for native code.

See the [server architecture](docs/architecture.md), [general scene guide](docs/generalization.md), and [release readiness notes](docs/release-readiness.md) for validation levels and backend limitations.

## Development and contributions

Create a development environment in the project root and run the checks:

```powershell
py -3.12 -m venv .venv
.venv\Scripts\python.exe -m pip install -e ".[dev]"
.venv\Scripts\python.exe -m unittest discover -s tests -q
.venv\Scripts\python.exe scripts/check_repository.py
```

Install `.[geometry]` as needed for geometry tests. Unit tests use mock engines and synthetic fixtures. Native validation requires locally installed software and licenses; see the [development guide](docs/development.md) for the steps.

Source code, documentation, generic examples, and tests are tracked in Git. Project data, archives, personal configuration, runtimes, and generated artifacts belong in the ignored `local-data/` directory. Include reproduction steps and validation details with contributions, and keep real customer models and vendor assets on your local machine.
